# 卡牌工坊技术框架 V0.1

> V0.2 版本说明：本文件保留旧版技术基线。最新玩法见 [竞技玩法与重复卡处理](competitive-gameplay.md)。新的手动激活允许在有限行动下同回合继续加工，不能与下文旧版的“轮末产出”规则混用。合成、销毁回收、公平挑战与计时接口尚待补充实现。资产归属、事务、幂等与账本原则仍适用。


本文件描述拟开发的架构，不代表对应服务或功能已经实现。当前只有设计文档、示例配置和设计校验脚本。

## 1 先实现规则 再实现多人资产

分成三个层次：

- 内容层：物种、配方、专精、目标模板、卡池权重。使用有版本的配置，不能在页面组件中散落规则。
- 规则层：纯函数处理一轮生产、验证目标、计算消耗。相同状态、配置版本和命令应得到相同结果。
- 资产层：账号、库存、卡牌所有权、订单预算、交易和账本。正式世界由服务器决定结果。

本地原型可以保存浏览器进度，但它不是联网经济的资产来源。联机测试使用独立数据库和新资产，禁止直接导入未经服务端验证的本地存档。

建议结构是在开发阶段创建，不是当前已存在的代码目录：

~~~
apps/web                   浏览器界面和本地原型适配器
apps/server                HTTP API、身份校验和事务编排
packages/core              生产规则、目标验证和领域类型
packages/content           已校验的版本化游戏配置
packages/contracts         API 输入输出类型及校验
tests/integration          结算、并发和恢复测试
~~~

规则层优先使用 TypeScript。服务端采用单体服务与 PostgreSQL；不在首版引入微服务、消息队列、撮合引擎或实时多人同步。具体 UI 框架与依赖版本在原型实现时选定。

首版材料按同类可堆叠资产处理，不做每一单位材料的品质、来源或随机词条。
卡牌必须区分模板与实例。出售某个实例不能错误地转移同种物种的其他卡牌。

## 3 生产规则

一轮的顺序：

1. 验证运行归属、状态、版本、回合数和本轮调整额度。
2. 校验工位、参与实例、唯一性、配方和优先级。
3. 复制轮初库存为可消耗库存，创建空的本轮产物缓冲区。
4. 按优先级逐卡执行；一张卡最多执行一次。
5. 足量原料才一次性扣除，产物只放入缓冲区；不足则整次跳过。
6. 全部加工完毕后合并缓冲区，推进回合和版本，记录事件。
7. 输出玩家可见状态及预览信息；不能从客户端接受自报的产量或余额。

邻接效果在未来加入时必须声明读取哪个阶段的快照；每个效果有单轮触发上限。
禁止递归触发“产物立刻再加工”，防止因连锁产生无限资源。
核心函数不读系统时间、不直接操作数据库、不调用随机数或网络。

内容更新不改变进行中生产的规则：每次运行固定配置版本与卡牌能力快照。
旧版本在所有关联运行结束前保留，避免玩家投入原料后配方突然变化。

### 生产状态与资源

WorkshopRun：ACTIVE → SETTLED。
主动结束或过期也是一次带原因的 SETTLED，而不是撤销已经发生的生产。这样不会通过选择性回滚获利。

正式生产创建时：

- 冻结参加的卡牌实例。
- 从可用库存转出投入物，记入该运行的托管库存。
- 建立唯一的活动运行，避免同一卡牌在多个标签页同时生产。

每个有效回合只更新运行的托管库存。最终结算把剩余原料和已生成产物转回玩家库存，并释放卡牌。
再次请求同一个结算返回原回执，不能再次入库。断线恢复读取服务端现状，而不是重新模拟客户端动作。

练习运行不读取或写入正式库存、成长、研究点、金币或订单进度。

## 4 卡牌 抽卡与培养

实例占用状态：IDLE、WORKING、LISTED。培养只允许在 IDLE 的原子操作中发生，不需要制造一个长期阻塞的 GROWING 状态。

培养事务同时验证实例归属、版本、成长资格和材料成本；扣费与分支变更同时提交。
挂牌上的能力快照不可变。改培养或改价必须先下架，不能让买家看到一种属性却买到另一种。

开包事务：

1. 以用户、操作和幂等键去重。
2. 校验卡包所有权与未开启状态，固定卡池版本。
3. 服务端按整型权重抽取，消耗卡包、创建实例、记录结果与来源。
4. 动画只播放已经保存的结果；断网重试拿回同一个回执。

不要把浏览器随机数或动画终点当成正式抽卡结果。服务端可使用 Node.js 的 crypto.randomInt；该接口使用上界不包含的整数范围，并避免取模偏差。[Node.js Crypto 文档](https://nodejs.org/api/crypto.html#cryptorandomintmin-max-callback)

JSON 中权重用于设计校验，不是已经运行的抽卡服务。

## 5 市场交易与系统订单

### 一口价市场

挂牌状态：ACTIVE → SOLD 或 CANCELLED。
MVP 材料按整包出售，不做一张挂牌的部分成交，减少结算分支。

创建挂牌时冻结资产并保存快照：
- 卡牌只能有一个有效挂牌。
- 材料的 available 减少、reserved 增加，不能只在 UI 中隐藏数量。
- 卖方必须拥有资产，绑定的新手卡不可挂牌。
- 售价为正整数。手续费、到账额和整包数量在确认前明确显示。

购买时，锁定挂牌与资产，再按固定账号顺序锁定相关余额；验证状态、所有权、买方余额和非自买。
在一个数据库事务中完成以下变更：

- 买方扣除全价。
- 卖方增加成交价减手续费。
- 手续费进入系统回收账户。
- 卡牌所有权或托管材料转给买方。
- 挂牌改为 SOLD，写入成交、资产账本及幂等回执。

金额全部为整数最小单位；手续费采用配置化整数比例及明确舍入规则。总价、数量及乘法中间值须限制在数据库与 API 的安全范围内。

交易中的金币恒等式：买方减少额 = 卖方增加额 + 系统回收额。
资产恒等式：卖方托管减少量 = 买方库存增加量。

PostgreSQL 的 FOR UPDATE 行锁可以阻止并发事务同时修改目标行；多对象锁应使用一致顺序，事务中不能等待玩家确认。[PostgreSQL 显式锁文档](https://www.postgresql.org/docs/current/explicit-locking.html)

锁之外还需要唯一约束、非负约束和状态条件更新；不是加一把锁就代表交易已安全。

### 系统订单

系统订单不是玩家挂牌，界面与数据都分开。

目标生成与报酬公式读取版本化配置。固定规则成本可用于报酬设计，不能读取某条玩家高价挂单就抬高系统兑付。
创建可领取订单不自动增发货币；领取时原子预留对应周期的金币和研究点预算。
完成时同时扣除交付物、消耗预算、发放奖励。过期或放弃只能释放一次预留。
配额耗尽时明确显示，不偷偷降低已经领取订单的报酬。

市场需求调节与奖励公式属于待模拟系统，现有设计校验脚本不证明长期经济稳定。

## 6 接口边界

拟定路由：

| 操作 | 路由 |
| --- | --- |
| 获取内容版本与卡池 | GET /api/v1/content |
| 获取我的资产 | GET /api/v1/inventory |
| 创建正式或练习生产 | POST /api/v1/workshops |
| 调整并推进一轮 | POST /api/v1/workshops/:id/rounds |
| 结算或提前结束 | POST /api/v1/workshops/:id/settle |
| 开包 | POST /api/v1/packs/:id/open |
| 选择或转换专精 | POST /api/v1/cards/:id/specialize |
| 读取、领取和交付订单 | GET /api/v1/contracts，POST /api/v1/contracts/:id/claim 或 deliver |
| 查询市场 | GET /api/v1/listings |
| 挂牌、购买、下架 | POST /api/v1/listings，POST /api/v1/listings/:id/buy 或 cancel |

所有资产变更要求身份验证和幂等键；涉及可变对象的命令带 expectedVersion。
同一个幂等键配不同请求体应拒绝，同请求体重放应返回原结果。
所有对象操作检查服务器会话中的用户身份，不能相信请求体的 ownerId。
HTTP 请求超时不代表交易失败；客户端通过操作回执查询结果。
Cookie 会话还要处理 CSRF、过期、退出与 HTTPS。接口限流不能替代所有权校验或事务约束。

## 7 自动目标生成

分两阶段，避免首版就开发庞大的求解器：

- P0 从已知可行计划和模板生成目标，使用确定性模拟核验。
- 后续引入受限搜索，在配方、原料、回合数和卡位条件下求可达目标。
- 随机变化后重新验证可达性；不能只随机几个数便发布。
- 生成的正式订单还需校验奖励预算、投入估算和重复目标分布。
- 记录目标配置、规则版本和验证见证，方便回放问题。

离线目标模拟不能自动验证多人市场价格、玩家兴趣或长期经济均衡。

## 8 测试与实施顺序

P0 规则测试：
- 产物不能在当轮再次消耗。
- 材料不足时原料不被部分扣除。
- 改变优先级得到不同结果，目标有可行方案。
- 初始库存、数量、卡位、优先级和回合数合法；非法状态拒绝。
- 换牌或交换位置不复制实例。
- 输入状态不被模拟函数修改。

P1 资产测试：
- 生产只结算一次，练习不能产出正式资产。
- 培养与挂牌冲突时最多一个成功。
- 开包请求重试不会产生多个实例。
- 系统订单预算不能超发，释放预留不能重复。
- 材料与卡牌消耗有完整账本。

P2 并发和恢复：
- 多人同时购买同一挂牌，只有一个成功。
- 买卖双方交叉交易、购买与下架竞态。
- 在扣款、转移、记账任一步注入失败，验证全部回滚。
- 断线、过期生产结算、重复回执与内容版本变更。

当前可运行的脚本仅检查示例配置和基础生产规则：
node scripts/validate-design.mjs

当前尚无浏览器页面、账号服务、数据库、真实抽卡、养成分支或交易市场，不能将设计测试通过表述为游戏已可玩。
