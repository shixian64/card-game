# 星序 ASTERIA｜O0 代码核实与 v1 基线

日期：2026-10-15（America/Denver）

范围：OPT-1 的 O0；不是 O1～O8 已实现声明，也不是平衡验收通过声明。

## 1. 结论与范围

支持重做卡牌内容与机制，但不能照 OPT-1 原文直接全量替换。当前 v1 在同预算阵容差异、野怪门槛、品质收益与换边一致性上都有可复现问题。

本轮只修复一个既有 HTTP 错误分类，新增离线观测、测试与报告。没有修改战斗规则、卡牌、品质、星级、经济数值、房间状态机或回放格式；没有新增公开匹配。没有执行 build / tsc / dev:local / Docker 构建，没有读取 `.env`、真实数据库或凭据，没有 reset / clean / 提交。

开工 HEAD：`cfcd349`。工作树原本包含大量修改及未跟踪文件；原样保护。不能把 HEAD 本身当作本次运行源码，报告另外记录了运行时文件 SHA-256。

## 4. 基线方法与证据边界

### 4.1 合法牌组与预算

五套 v1 代理牌组，每套 **八个不同卡种**，包含前排和远程，部署六人来自牌组。测试在独立 `:memory:` SQLite 中构造拥有这些卡的档案，并调用实际 `createDuelService().loadout()` 验证；移除任一卡后实际服务拒绝。不涉及真实账号或数据库。

这只是“拥有八卡种、最高 Q5”的离线夹具，不说明真实新用户都拥有这些卡。八卡组完整列表、六人出战列表和备用两卡均写入 JSON。

矩阵有三个成本层，层内双方成本相同：

| 层 | 阵容 | 六人采购总成本 |
| --- | --- | ---: |
| q1_s1 | Q1，全一星 | 60 |
| q3_s1 | Q3，全一星 | 72 |
| q1_core2 | Q1，第一名前排二星，其余一星 | 80 |

采购总成本按 `duelShopPrice(quality) × 3^(stars−1)` 计算；矩阵不扣免费副本，也不模拟采购路径。品质/星级敏感性实验明确是**不同预算**，不能用于声称同预算收益合理。

### 4.2 站位、先手与换边

每套阵容固定生成 20 组互异合法站位：约 2/3 前后排分区，约 1/3 全场散布。采样用固定 xorshift，禁止 `Math.random`。

每个对局站位块覆盖两种 combatSeed 奇偶，再真实交换双方输入，合计四次模拟。比较换边一致性时同时翻转 seed 奇偶，以保持同一个实际玩家的先手。

**当前战斗内核只使用 seed 的奇偶，20 或 300 个不同数字不代表相应数量的独立战况。** 本报告不把这四次或重复 seed 当作独立真人样本，不报告虚假的二项分布置信区间。主要矩阵为 15 个不重复对局（含五个自对局）× 3 个成本层 × 20 站位块 × 4 = 3,600 次。

### 4.3 其他实验

- 固定阵容品质复核：沿用旧报告阵容与站位，5 档 × 300 seed = 1,500 次；专门展示报告漂移和重复样本。
- 核心星级敏感性：3 个星级 × 20 站位块 × 4 = 240 次。
- 野怪：5 阵容 × 3 营地 × 2 投入档，以及五套两张免费 Q1 副本，合计 2,800 次。低投入为 Q1 全一星；较成熟快照为 Q3，R4/R7 前排二星、分别带此前可得的一/两件装备。
- 装备：五阵容各测试无装备及六种单件装备，对相同 Q3 远程双坦阵容，合计 2,800 次。按固定持有者规则分配，不声称是最优分配或完整装备矩阵。

野怪快照不是十轮经营轨迹；没有在假经营代码上补一套新的商店/合星服务来冒充权威流程。全十轮真实采购、卖卡、锁店、刷新策略仍待独立验证。

## 5. 当前数值结果

### 5.1 Q3 全一星同预算矩阵

单元格为行阵容胜率；平局单列记录在 JSON。对角线为同阵容双方对称汇总，不代表某个固定座位胜率。每个非对角对局有 20 个站位块、80 次模拟。

| 行胜率 % | 月盾混编 | 日系火力 | 森林前排 | 远程双坦 | 刺客切后 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 月盾混编 | 50 | 100 | 35 | 45 | 86.25 |
| 日系火力 | 0 | 50 | 86.25 | 7.5 | 0 |
| 森林前排 | 65 | 13.75 | 50 | 30 | 95 |
| 远程双坦 | 55 | 92.5 | 70 | 50 | 53.75 |
| 刺客切后 | 13.75 | 100 | 5 | 46.25 | 50 |

这些阵容不能当作 v2 原型：v1 日系没有灼烧，月系没有主动控制，森林没有成长；本表**不能验证或否定 v2 的五角克制环**。它能证明当前同预算的阵容间差异很大：远程双坦对其余四阵容均值约 67.81%，日系火力约 23.44%。这里只比较五套指定阵容，不代表找到了全局最优。

### 5.2 超时、回合与性能

| 矩阵层 | 达到回合上限 | 比例 |
| --- | ---: | ---: |
| Q1 全一星 | 21 / 1,200 | 1.75% |
| Q3 全一星 | 24 / 1,200 | 2.00% |
| Q1 核心二星 | 52 / 1,200 | 4.33% |

全部实验混合统计：超时约 **2.10%**，平均 **12.72 个逻辑回合**；混合值只描述此测试集，不能替代分组指标。单场模拟 P50 **2.62 ms**、P95 **4.70 ms**（不含 JSON 序列化、SQLite、网络与渲染，不是服务器吞吐率或压测结论）。没有依据提前引入 worker_threads。

### 5.3 品质与星级

同旧报告固定 Q3 敌阵对比，当前 Q1～Q5 胜率为 **0 / 50 / 50 / 100 / 50%**。每档 300 次只有 **两种完整回放哈希**。旧报告的 `0 / 0 / 50 / 100 / 100%` 已不能复现；不确定哪个历史改动引起差异，没有倒推归因。

新的多站位核心星级实验为同 Q3，只有第一名前排升星：

| 核心星级 | 己方总成本 | 对方总成本 | 胜率 |
| --- | ---: | ---: | ---: |
| 一星 | 72 | 72 | 45% |
| 二星 | 96 | 72 | 72.5% |
| 三星 | 168 | 72 | 87.5% |

这不是“全队升星”、不是同预算、也不是 OPT-1 星级验收门槛的正式验证。品质收益不单调需要先排查受击回能、选敌和先手导致的节奏变化，不能直接认为高品质数值越高必然越强。

### 5.4 野怪与装备

当前五套阵容在所有低投入/较成熟快照上对 R1/R4/R7 均为 **100% 通过**；五套两张免费 Q1 副本对 R1 也均为 100%。这扩大了“野怪过于宽松”的证据，但依旧不是所有新手牌组或实际玩家通过率。

单件装备相对无装备，在指定持有者和对手下胜率变化范围 **−2.5 ～ +15 个百分点**。例：日系火力带石脉甲为 +15，月盾混编带回响棱为 −2.5。不能据此认定该装备普遍过强/无用；应在 O5/O6 扩展对手与分配规则。说明“六件全是纯数值棒”不够准确：回能、开场盾和第三次普攻追加伤害已有触发行为，只是缺少状态和目标规则变化。

## 6. 新发现：v1 换边一致性不成立

在交换双方输入、同时翻转先手奇偶后，归一化胜负不一致：

| 矩阵层 | 不一致 / 配对比较 |
| --- | ---: |
| Q1 全一星 | 48 / 600 |
| Q3 全一星 | 56 / 600 |
| Q1 核心二星 | 63 / 600 |

这不等于 A 方总体胜率偏高，但足以反驳“所有输入旋转换边都保持镜像结果”。现有镜像胜率接近 50% 的测试没有覆盖这个更强性质。

最小已保存反例：Q3 月盾混编的第 5 号站位块（从 0 开始计数）。原输入 seed=0，左侧阵容获胜；双方输入交换、seed=1 后，原右侧阵容获胜。两次 winner 都是物理 A，因此归一化结果相反。

将第二次状态旋转回原视角，前三帧一致，**第 4 帧 / 第 1 逻辑回合**开始不同：薄雾来信原路径闪现后普攻烛羽灵狐，镜像路径却闪现后继续移动接近星河守望。下一阶段应从闪现落点、选敌与方向 tie-break 的最早分歧追踪，不应先增加随机或调数值。O0 只记录，**不修 v1 规则**；golden 保留既有语义，v2 可单独修正。

## 7. OPT-1 与代码不一致或需要修订的内容

1. **职业与插画耦合属实。** 实际统计坦克 7 / 战士 6 / 射手 5 / 法师 13 / 刺客 5；月只有坦克/刺客、日只有射手/法师、森只有战士/法师。六幅插画对应五种主动模板，不应把“六个插画配置”说成六种独立机制。
2. **技能节奏同质属实，但并非所有单位严格固定节奏。** 射手羁绊、装备回能和受击回能已有差异；当前仍只有共同的 100 能量上限。
3. **旧平衡报告已漂移，且 seed 重复。** 需以本轮运行及文件哈希为新基线；旧报告保留，不覆盖原始证据。
4. **旧经营模拟不是合法八卡池。** `STANDARD_TEAM` 只有六项，`slice(0,8)` 仍是六项；装备始终为空，不能声称已验证装备经营。另有 B 玩家野怪胜负把玩家所在 A 侧误写成 `simB.winner==='B'` 的诊断字段；本轮不改旧脚本，避免改变历史报告生成口径。
5. **可信代理限流已有实现与真实 HTTP 测试。** `client-address.mjs` 从可信 socket 反向解析转发链；不要重复造轮子。部署时的实际 `TRUSTED_PROXIES` 未读取、未验证。
6. **规则版本只是记录，尚无分流。** `duel_rooms.rules_version` 已有，`frozen_input` 无战斗版本；重算直接调用当前模拟器和当前营地表。新增 v2 前必须按房间生命周期隔离卡牌、职业、技能、羁绊、装备、星级、野怪及 UI 说明，不仅增加一个字段。未冻结的旧房间后续轮次同样应保持 v1。
7. **“只重做内容层”需要澄清。** O2/O3 涉及引擎、协议、回放与前端适配；准确范围是保留产品骨架、扩展战斗机制，而非纯数据替换。
8. **八个核心状态不足以完整描述卡表。** 还需明确成长、吸血、反射、播种、不可选中的通用 modifier/trigger 语义，施加/到期顺序、死亡触发与致命保护优先级，以及反伤触发递归上限。
9. **O2 体积门槛有歧义。** 同时返回完整旧 frames 和新增事件不可能凭空减少总响应；应分别比较事件格式与旧格式，或为不同客户端只返回一种表示。检查点、增量字段及寻址索引也需算入字节数。
10. **当前主 UI 已读取战斗技能文案。** `data.ts` 仍有算分遗留是维护风险，不等于已证明主页面正在显示“+12 分”。移除前应追踪旧 `App.tsx`、`engine.ts` 与测试引用，不能直接删字段。
11. **dist 与 tsbuildinfo 已忽略。** `.gitignore` 已包含 `dist/` 和 `*.tsbuildinfo`。不需要重复修复。
12. **构建/实机仍未验证。** 测试里 TSX 语法检查不等于全量类型检查，静态 UI 测试不等于双人实机验收。源码中存在邀请码流程，没有公开匹配；“最大留存风险”是产品假设而非本轮数据结论。
